# Universal Hub + C++ Client Library — концепция V1

**Статус:** концепция V1 согласована и актуализирована после завершения архитектурного обсуждения, 17 октября 2026 года.  
**Назначение:** зафиксировать согласованные требования и поведение Universal Hub и C++ Client Library как основу для архитектуры, технического плана и реализации.  
**Граница документа:** поведение Hub Server и клиентской библиотеки. Конкретные классы, формат бинарных пакетов, алгоритмы и исходный код здесь не проектируются.

> **Важно:** это **первая версия самого Universal Hub**, а не диспетчеризация V1. Диспетчеризация V1 завершается по первоначальному плану с MQTT. Новый Hub планируется как самостоятельный компонент для последующего перехода диспетчеризации на него (ориентир — диспетчеризация V2). Если потребуется, старые компоненты диспетчеризации можно переписать. Требования диспетчеризации V1 не ограничивают архитектуру Hub.

## 1. Назначение и границы — согласовано

- Разрабатываем **собственный локальный хаб** и **собственную C++ клиентскую библиотеку** для взаимодействия с ним.
- Это самостоятельные переиспользуемые компоненты: хаб **не привязан** к Modbus, устройствам, диспетчеризации, дашбордам, авариям или любому конкретному оборудованию.
- Все клиенты и Hub Server работают **на одной Linux-машине**. Удалённые подключения, доступ с других серверов и внешние сетевые API не предусматриваются. Связь с внешним оборудованием при необходимости организуют другие приложения, а не хаб.
- **Не опираемся на MQTT** и не пытаемся копировать его возможности, совместимость или протокол. Разрабатываем только необходимое нам поведение.
- В основе — публикация значений, подписка на обновления и запрос последних сохранённых значений.
- Внутренние решения ориентируем на хорошую производительность, но не на преждевременную микрооптимизацию.

### Предварительно выбранное техническое направление

Для локального межпроцессного обмена выбран **Unix Domain Sockets** и собственный компактный **бинарный протокол**. Детали транспорта, бинарных пакетов и конкурентности будут разобраны на архитектурном и техническом этапах. Это не повод заранее добавлять дополнительные транспортные варианты.

## 2. Данные и идентификаторы — согласовано

### 2.1. Числовые ID

- Метрика идентифицируется **`uint32_t`** (32-битный беззнаковый ID).
- Хаб обрабатывает только числовой ID, тип значения и значение. Он не знает имя метрики и её назначение.
- **Строковые пути/«топики» остаются вне хаба.** В использующем его приложении отдельный каталог может сопоставлять строковый путь и ID в обе стороны; искать по маске вроде `+/+`; возвращать клиенту список ID. Сам хаб такого поиска не делает.
- Назначение ID и исключение конфликтов — ответственность приложения, использующего хаб.
- Не вводим обязательную регистрацию метрик и отдельное хранилище их свойств.

### 2.2. Последняя **десятичная цифра** задаёт режим

| Окончание ID | Правило |
|---|---|
| `0` | **Transient**: передать активным подписчикам, **не сохранять** последнее значение. |
| `1` | **Stored**: передать активным подписчикам **и сохранить** последнее значение. |
| `2`–`9` | Зарезервированы; публикация с такими ID в первой версии считается некорректной. |

Примеры: `1250` — только передача, `1251` — передача и хранение.

Режим определяется из `ID % 10`, **не из младших бит**. Выбор десятичной цифры сделан сознательно ради простоты и удобства формирования ID. `1250` и `1251` — **разные самостоятельные ID**, а не разные режимы одного и того же объекта.

### 2.3. Предпоследняя десятичная цифра задаёт тип данных

Тип определяется по `(ID / 10) % 10` без обязательной регистрации метрик:

| Предпоследняя цифра | Тип значения |
|---|---|
| `0` | **Integer** — `int64_t` |
| `1` | **Float** — `double` |
| `2` | **String** — UTF-8 строка |
| `3`–`9` | Зарезервированы и пока не используются |

Например: `1234501` — целое число с хранением, `1234510` — вещественное число без хранения, `1234521` — строка с хранением. Режим хранения и тип входят в сам ID; изменить любой из них без изменения ID нельзя.

Для обычных логических значений допустимы целые `0`/`1`; отдельный тип `bool` пока не нужен. Все значения строками не передаём. **Тип не требуется повторять отдельным полем каждой публикации.**

Составной формат ID намеренно основан на **десятичных цифрах**, а не на битовых полях. Хаб не сопоставляет окончания ID с названиями метрик и не поддерживает реестр их типов.

## 3. Публикация и подписки — согласовано

1. **Publish:** любой подключённый клиент может публиковать значение по любому **разрешённому** ID. Владельцы ID на уровне хаба не регистрируются.
2. **Subscribe:** подписка принимает **только список числовых ID**. Один ID — список из одного элемента. Подписок по маскам, строковым путям или диапазонам ID в хабе нет. Повторная подписка на уже подписанный ID не создаёт дубликата и не отправляет его сохранённое значение второй раз; для повторного чтения есть `Get`.
3. **Можно подписаться на ID до появления значения.** Когда публикация поступит, подписчик её получит.
4. **Фильтрация повторяющихся значений — у отправителя.** Хаб сам не сравнивает старое и новое значение и пересылает каждую полученную публикацию.
5. **Обязательного подтверждения каждой публикации нет.** Публикация не гарантирует обработки всеми подписчиками; ошибки локальной отправки/соединения могут быть сообщены клиенту.
6. **Unsubscribe:** отмена подписки для списка ID. Точная форма API ещё не определена.

Хаб доставляет публикацию **активным подписчикам указанного ID**, сохраняя новое значение только для ID, оканчивающихся на `1`.

## 4. Получение последних значений — согласовано

### 4.1. Одна операция `Get([IDs])`

- Используем одну команду `Get([1001])` либо `Get([1001, 2001, 3001])`; отдельной операции `GetMany` нет.
- `Get` — **асинхронная команда «пришли мне сохранённые значения этих ID»**, а **не** вызов с ожиданием ответа.
- Хаб отправляет найденные сохранённые значения **только клиенту, вызвавшему `Get`**, используя **ровно тот же формат и канал входящих значений**, что и обычные публикации. Другим подписчикам значения от `Get` не рассылаются.
- Отправка ответа на `Get` не считается новой публикацией и не меняет хранилище.
- Для отсутствующего значения или ID режима `0` хаб **ничего не отправляет**. Специальных `NotFound`, `NotStored` и ошибок отсутствия значения нет.
- Нет идентификаторов запроса, подсчёта пришедших значений, отдельного сообщения «Get завершён», ожидания или таймаута завершения `Get`. Клиент просто продолжает работу и принимает входящие сообщения.
- **Подписка не обязательна для `Get`:** запросивший клиент получает найденные значения напрямую.

### 4.2. Начальные значения при `Subscribe`

При подписке на список ID хаб автоматически отправляет подписчику **имеющиеся сохранённые значения** по этим ID, затем доставляет новые публикации. Формат входящих значений общий для `Publish`, `Get` и начальных значений `Subscribe`.

При оформлении подписки не должно возникать промежутка, в котором публикация теряется между начальным снимком и живыми обновлениями. Реализацию этого свойства определим позже.

### 4.3. Очистка сохранённых значений — `Clear([IDs], unsubscribe)`

Добавлена единая операция `Clear`, принимающая список числовых ID и флаг:

- **`Clear([IDs], false)`** — удаляет существующие сохранённые значения, **не меняет подписки** и не отправляет уведомления. Если значение отсутствует либо ID несохраняемый, ничего делать не требуется.
- **`Clear([IDs], true)`** — удаляет сохранённые значения **и принудительно отменяет текущие подписки** на указанные ID, в том числе если значения отсутствуют. Затронутым подключённым клиентским библиотекам отправляется служебное уведомление об отмене; библиотека исключает ID из списка подписок для автовосстановления и уведомляет приложение через callback, например `onIdRemoved(id)`.

`Clear` **не запрещает повторные `Publish` и `Subscribe`** по тем же ID и не регистрирует удалённые метрики. `onIdRemoved` сообщает именно о принудительной отмене подписки, а не о вечном удалении ID.

Если клиент был отключён в момент `Clear(..., true)`, хаб не хранит для него событие удаления. После восстановления его библиотека может повторить прежнюю подписку. Это **сознательно принятое ограничение первой версии**, а разбор повторного использования ID относится к приложению.

## 5. Отключения и ошибки — согласовано

### 5.1. Отключение клиента/источника

- При отключении клиента хаб убирает его подписки; для него не создаётся постоянная сессия и не копятся пропущенные сообщения.
- Сохранённое значение с окончанием ID `1` **остаётся**, даже если опубликовавший его клиент отключился. Хаб не знает срок актуальности и не определяет исправность источника.

### 5.2. Перезапуск хаба

- Последние значения находятся **только в RAM**. После перезапуска хранилище пустое, постоянное хранение на диск не требуется.
- **Клиентская библиотека** обнаруживает разрыв соединения, сообщает приложению об отключении, пытается переподключиться, восстанавливает подписки и сообщает о восстановлении соединения.
- При необходимости повторной публикации собственных текущих значений после восстановления соединения решение принимает **клиентское приложение/источник**. Сам хаб не опрашивает отправителей и не восстанавливает значения автоматически.

### 5.3. Медленные потребители

- **Не создаём в хабе отдельные очереди доставки сообщений для клиентов.** Допускается небольшая входящая очередь на стороне клиентской библиотеки, но её устройство пока не утверждено.
- Передача из хаба не должна блокировать обслуживание других клиентов. Если отправка клиенту невозможна из-за заполнения системного буфера, хаб **разрывает соединение** с ним, а не ждёт без ограничения.
- Хаб не ведёт историю и не пытается догнать отключённого получателя. Клиентская библиотека может переподключиться и восстановить подписки.

## 6. C++ Client Library — согласовано

Клиентская библиотека предоставляет приложениям единый C++ интерфейс к Universal Hub, скрывая работу с Unix Domain Sockets и бинарным протоколом. Она **не является отдельным процессом** и не содержит предметной логики использующего её приложения.

### 6.1. Получение значений

- Приложение получает входящие значения через **callback** (обработчик, который вызывает библиотека).
- Для обычных публикаций, начальных значений `Subscribe` и результатов `Get([IDs])` используется **один механизм обработки входящих значений**.
- Внутри библиотеки **допускается небольшая ограниченная очередь**, чтобы чтение из сокета не зависело напрямую от длительности обработчика приложения. Обязательность очереди, её размер и поведение при переполнении определим на архитектурном этапе, не утверждая их заранее.

### 6.2. Хранение значений

- **Кеша последних значений в Client Library нет.** Последние значения с разрешённым хранением находятся в Hub Server.
- Если приложению нужно получить сохранённые значения, оно выполняет `Get([IDs])`, а сами значения затем поступают через общий обработчик входящих данных.
- Само клиентское приложение при необходимости может хранить собственное состояние; хаб и библиотека не навязывают ему такую модель.

### 6.3. Публичные операции

- `Publish(ID, value)` — передать значение хабу.
- `Subscribe([IDs])` — подписаться на список числовых ID.
- `Unsubscribe([IDs])` — отменить подписки на перечисленные ID.
- `Get([IDs])` — попросить хаб отправить имеющиеся сохранённые значения **только запрашивающему клиенту**.
- `Clear([IDs], unsubscribe)` — удалить сохранённые значения, при `unsubscribe=true` также отменить текущие подписки на перечисленные ID.

Операции **асинхронны по смыслу**: они не ждут, пока хаб обработает публикацию или вернёт все запрошенные значения. В частности, `Get` не возвращает массив значений из вызова и не требует специального ответа о завершении. Библиотека может сигнализировать о локальной невозможности отправки, например при отсутствующем соединении.

### 6.4. События принудительной отмены подписок

При `Clear([IDs], true)` библиотека получает служебное уведомление, удаляет отменённые ID из списка автоподписки и вызывает callback приложения, например `onIdRemoved(id)`. Для отключённых клиентов хаб не сохраняет ожидающие уведомления.

### 6.5. Соединение и многопоточность

- **Один экземпляр клиентской библиотеки использует одно UDS-соединение** с Hub Server.
- Публичные операции этого экземпляра должны быть **потокобезопасными** для вызовов из разных потоков приложения, без требования создавать по соединению на поток.
- Библиотека самостоятельно обнаруживает разрыв, уведомляет приложение, пытается переподключиться, восстанавливает оформленные подписки и сообщает о восстановлении соединения.
- Сообщения, не переданные во время отключения, **не накапливаются для последующей отправки**. После переподключения повторная публикация необходимых собственных значений — ответственность приложения.

### 6.6. Выбранный транспорт и детали реализации

Для первой версии используем **Unix Domain Sockets в режиме `SOCK_SEQPACKET`** и собственный компактный бинарный протокол. Отдельный TCP-транспорт, общую память и POSIX-очереди сообщений **не реализуем**. Формат пакетов, предельный размер и модель потоков определяются в архитектуре и техническом проекте. Небольшая ограниченная очередь приёма в Client Library допустима, но не обязательна до выбора реализации. Выбранный транспорт сам по себе не означает гарантированной доставки каждой публикации.

## 7. Явно не включаем в первую версию Hub

- MQTT-совместимость и MQTT-специфичные возможности.
- Удалённые клиенты, сетевые API и работу между разными машинами.
- Работа с именами устройств, строковыми топиками, шаблонами и их поиском на стороне хаба.
- Регистрация владельцев ID, пользователей и роли.
- История измерений, гарантированная доставка каждой публикации, постоянные сессии, хранение пропущенных сообщений.
- Сохранение последних значений на диск, кластеризация, резервирование.
- Специальная подсистема команд/Request-Reply как отдельная сущность хаба: сообщения с ID режима `0` могут использоваться приложениями для команд; сопоставление команд и результатов относится к прикладной логике.
- Очереди отложенных публикаций, автоматическую повторную отправку после переподключения и историю очисток, пока клиент был отключён.
- Сложные способы фильтрации, автоматическое подавление одинаковых публикаций, вычисляемые метрики.
