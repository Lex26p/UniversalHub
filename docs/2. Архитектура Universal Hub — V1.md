# Universal Hub + C++ Client Library — архитектура V1

**Статус:** согласованная архитектура, итоговая сверка 17 октября 2026 года.  
**Назначение:** закрепить внутреннюю организацию локального Hub Server и C++ Client Library, не подменяя её технической реализацией.  
**Связанный документ:** «Концепция Universal Hub — V1».  
**Граница:** Universal Hub — самостоятельный компонент, **не часть диспетчеризации V1**. Документы диспетчеризации не изменяются.

## 1. Общая структура — согласовано

### 1.1. Компоненты

1. **Hub Server:** один самостоятельный C++ процесс, принимающий локальные соединения, хранящий последние значения выбранных ID и доставляющий публикации подписчикам.
2. **C++ Client Library:** библиотека для приложений, скрывающая детали соединения и бинарного протокола, обеспечивающая получение значений и восстановление подписок.
3. **Общий код протокола:** совместно используемые определения, сериализация и разбор сообщений без дублирования на сервере и у клиента. Это не отдельный процесс.

Hub Server и Client Library — раздельные результаты сборки. Все процессы работают **на одной Linux-машине**. Удалённый TCP-доступ, совместимость с MQTT и функции конкретных прикладных систем не предусматриваются.

### 1.2. Границы процессов и соединений

- **Один процесс Hub Server** обслуживает все клиентские приложения.
- **Один двунаправленный Unix Domain Socket** на экземпляр Client Library, общий для входящих и исходящих операций.
- Одно приложение при необходимости может создать более одного клиентского экземпляра.
- Сервер не регистрирует «устройства», владельцев ID, категории сообщений, пути параметров или строковые топики. Их смысл определяют приложения.

### 1.3. Независимые обязанности сервера

- **Values:** последнее сохранённое значение по числовому ID.
- **Subscriptions:** сведения о том, каким активным клиентам отправлять обновления конкретных ID.

Существование подписки **не означает** существование значения, и наоборот. Отдельная регистрация метрик не требуется.

## 2. Транспорт и бинарный протокол — согласовано

### 2.1. Транспорт

- Используем **Unix Domain Sockets** в режиме **`SOCK_SEQPACKET`**.
- Передача сообщений локальная, двунаправленная, с сохранением границ и порядка пакетов внутри соединения.
- Внутри работает собственный **компактный бинарный протокол**, не производный от MQTT.
- **Максимальный размер одного сообщения ограничен**; конкретный лимит выбираем на техническом этапе.
- Ни хаб, ни библиотека не обязаны автоматически разбивать большие списки ID или другие операции на части. Если операция не помещается, вызывающее приложение само решает, как её разделить.

### 2.2. Идентификатор и тип значения

ID — **`uint32_t`**. Две младшие *десятичные* цифры кодируют свойства:

| Цифра | Код | Смысл |
|---|---|---|
| Последняя (`ID % 10`) | `0` | Публикация без сохранения |
| Последняя (`ID % 10`) | `1` | Публикация с сохранением последнего значения |
| Предпоследняя (`(ID / 10) % 10`) | `0` | `int64_t` |
| Предпоследняя (`(ID / 10) % 10`) | `1` | `double` |
| Предпоследняя (`(ID / 10) % 10`) | `2` | UTF-8 `string` |

Остальные коды зарезервированы, но **не разрешены для публикации** в V1. В протоколе не требуется повторно передавать тип или режим отдельными полями. `1250` и `1251` — разные ID, а не два состояния одного ID.

Примеры:

| ID | Тип | Хранение |
|---|---|---|
| `1001` | Integer | Да |
| `1011` | Float | Да |
| `1020` | String | Нет |
| `1234521` | String | Да |

### 2.3. Кодирование значений

- `int64_t` и `double` передаются в **двоичном 8-байтовом** представлении.
- UTF-8 строка передаётся последовательностью байтов.
- Отдельную длину строкового значения **не добавляем без необходимости**: её можно получить из размера `SOCK_SEQPACKET` сообщения за вычетом служебных полей.
- Структура служебных полей, порядок байтов и конкретные ограничения кадров определяются техническим планом и реализацией протокола.
- Клиентская библиотека предоставляет **строго типизированный C++ API** и проверяет тип при работе с динамическими числовыми ID (совпадение типа с цифрой ID не всегда можно проверить компилятором).

### 2.4. Операции

| Операция | Поведение |
|---|---|
| `Publish(ID, value)` | Принять значение, сохранить при режиме `1`, отправить активным подписчикам |
| `Subscribe([IDs])` | Оформить подписки и передать имеющиеся сохранённые значения, затем будущие публикации |
| `Unsubscribe([IDs])` | Снять подписки вызывающего клиента |
| `Get([IDs])` | Отправить сохранённые значения **только запросившему клиенту** |
| `Clear([IDs], false)` | Очистить сохранённые значения, не меняя подписок |
| `Clear([IDs], true)` | Очистить значения и принудительно отменить существующие подписки на эти ID |

**Одна форма** `Get([IDs])` работает для одного и многих ID; отдельного `GetMany` нет. `Get` — асинхронная команда «пришли найденные значения», **не** вызов, который ожидает завершения или собирает результат. Отсутствующее или несохраняемое значение просто не отправляется; ответов `NotFound`, «конец списка» и корреляции запросов нет.

Новая публикация по ID, начальные сохранённые значения при `Subscribe` и данные по `Get` доставляются **одним форматом входящего Value**. Сообщения `Get` не считаются повторными публикациями и другим подписчикам не рассылаются.

Для обычной публикации нет обязательного подтверждения приёма сервером. Хаб не подавляет одинаковые значения — решение о публикации повторов принимает отправитель.

### 2.5. `Clear` и уведомление об отмене

- `Clear([IDs], false)` удаляет только сохранённые значения: подписки остаются, уведомлений нет.
- `Clear([IDs], true)` удаляет сохранённые значения и отменяет **активные** подписки на эти ID, даже если значение никогда не публиковалось или ID имеет режим `0`.
- При `Clear(..., true)` затронутым подключённым клиентам отправляется служебное уведомление об отмене. Client Library исключает отменённые ID из списка автоподписок и уведомляет приложение callback, например **`onIdRemoved(id)`**.
- `Clear` не запрещает новые публикации и новые подписки на тот же ID; хаб не создаёт «надгробий» удалённых ID или реестра метрик.
- Для клиента, **отключённого во время** `Clear(..., true)`, никакое уведомление не сохраняется. После восстановления клиентская библиотека может повторить старую подписку. **Это осознанный компромисс** ради простой локальной модели; корректное повторное использование ID — ответственность приложения.

### 2.6. Минимальные проверки входящего сообщения

Библиотека формирует кадры сама и предоставляет типизированные операции: приложение не должно вручную собирать бинарные сообщения. При этом **компилятор C++ не проверяет байты, прочитанные из сокета**, поэтому сервер выполняет минимальную проверку границ сообщения, его структуры и допустимых кодов операции/ID.

Некорректный бинарный пакет приводит к **закрытию соединения конкретного клиента**, а не к падению хаба. Корректный `Get` без сохранённого значения — не ошибка, никакого ответа не создаётся. Дополнительную сложную схему ошибок и попытки исправлять повреждённые сообщения не делаем.

## 3. Хранение значений в памяти — согласовано

### 3.1. Контейнер

- Используем стандартный **`std::unordered_map<uint32_t, Value>`**, а не массив по всему диапазону 32-битных ID и не упорядоченное дерево.
- **`Value` представляется `std::variant<int64_t, double, std::string>`**; дополнительных хранилищ по типам не создаём.
- Записи создаются **только** при публикации сохраняемого ID. Подписка на отсутствующий ID не создаёт Value.
- На повторную публикацию сохраняемого ID последнее значение заменяется новым. Если несколько клиентов публикуют по одному ID, действует последнее обработанное сервером значение.
- Метрики с режимом `0` в Values не помещаются.

### 3.2. Срок жизни

Значение сохраняется до следующей публикации того же ID, `Clear` или завершения Hub Server. Отключение клиента-отправителя **не удаляет** значение. После перезапуска сервера хранилище **пустое**; на диск последние значения не сохраняются.

Нет TTL, автоматического вытеснения, ограничения количества метрик, фоновой очистки или отдельного менеджера памяти. Размер одного значения ограничивается допустимым размером сообщения. Расход памяти измеряем в нагрузочных тестах.

## 4. Подписки и доставка — согласовано

### 4.1. Два индекса подписок

- **`ID → набор подписанных клиентов`** — для быстрого поиска получателей на публикацию; можно использовать `std::unordered_map`.
- **`Клиент → набор его ID`** — для быстрого снятия подписок при отключении клиента.

Это два согласованных представления одних подписок, не две отдельные системы доставки. При публикации хаб не перебирает всех клиентов.

### 4.2. Правила подписки

- Подписываемся **только по числовым ID**, включая отсутствующие значения; подписки по маскам и строковым путям в хаб не входят.
- Повторный `Subscribe` на уже подписанный ID **не дублирует** подписку, последующие уведомления и начальное сохранённое значение. Для повторного чтения есть `Get`.
- При первом `Subscribe` хаб отправляет существующие сохранённые значения по запрошенным ID, затем будущие публикации. Между начальной отправкой и регистрацией живой подписки **не должно теряться обновление**.
- `Unsubscribe` снимает только подписки вызывающего клиента.
- При разрыве соединения хаб удаляет подписки клиента. Постоянных сессий и доставки пропущенных сообщений нет.

### 4.3. Порядок обработки

Сообщения одному получателю доставляются **в порядке обработки их хабом**, пока соединение работает и доставка возможна. Это не означает одновременную обработку разными подписчиками и не предполагает гарантированного восстановления потерянных обновлений.

При `Clear(..., true)` сервер удаляет значения и подписки, затем посылает служебное уведомление затронутым клиентам. Новые публикации по отменённому ID не отправляются прежним подписчикам, пока они не оформят подписку вновь.

## 5. Конкурентность и ввод-вывод — согласовано

- **Один событийный поток** Hub Server для обработки клиентских сообщений, хранилища Values и индексов Subscriptions.
- **Неблокирующие `SOCK_SEQPACKET` + `epoll`** для обслуживания всех клиентских соединений. Начинаем с обычного **level-triggered** режима.
- Values и Subscriptions меняются только из этого событийного потока. Отдельные мьютексы вокруг этих структур для обычного пути обработки не требуются.
- При публикации сервер находит подписчиков и выполняет **неблокирующую отправку** каждому в пределах обработки события.
- Не создаём отдельные **прикладные очереди исходящих сообщений** на каждого клиента в хабе. Если сокет получателя временно не может принять сообщение из-за заполнения системного буфера, хаб **отключает этого клиента**, не блокируя остальных. Пропущенные публикации не сохраняются для повторной доставки.
- Не создаём по потоку на клиента, общий многопоточный пул хаба, lock-free структуры или shared memory. В будущем можно измерить производительность и пересмотреть устройство сервера, если возникнет реальная необходимость.

## 6. C++ Client Library и жизненный цикл — согласовано

### 6.1. Интерфейс и входящие значения

- Библиотека предоставляет `Publish`, `Subscribe`, `Unsubscribe`, `Get`, `Clear` и события состояния соединения.
- Поступившие значения передаются приложению через **callback** вне зависимости от того, возникли они вследствие публикации, подписки или `Get`.
- Для принудительной отмены подписки через `Clear(..., true)` предусмотрен **отдельный callback** `onIdRemoved(id)` (окончательное название API можно определить при реализации).
- Библиотека **не хранит кеш последних значений**; хранение — обязанность сервера для сохраняемых ID.
- Публичные операции **потокобезопасны**, одно соединение приходится на экземпляр библиотеки.
- **Небольшая ограниченная входящая очередь** между чтением сокета и вызовом обработчика **допускается**, но не утверждена как обязательная. Её необходимость и политика переполнения определяются при разработке Client Library.

### 6.2. Переподключение

- При потере соединения Client Library сообщает приложению о недоступности Hub, пытается переподключиться и после восстановления **автоматически восстанавливает список актуальных подписок**; приложение получает событие восстановления связи.
- **Непереданные операции не ставятся в очередь** для выполнения после переподключения: это касается Publish, Get, Clear и других разовых действий. Клиент получает информацию о локальной невозможности отправки.
- Список подписок хранится для переподключения, но принудительно отменённые через `Clear(..., true)` и сообщённые библиотеке ID из списка удаляются.
- Если сервер перезапустился, он потерял последние значения. Восстановление необходимых публикаций осуществляют сами клиентские приложения, а не сервер.
- Хаб не запоминает клиентов, отключённых в момент `Clear(..., true)`; когда библиотека их соединения возобновится, прежние подписки могут восстановиться. Специальных механизмов отслеживания удалений для отсутствующих клиентов нет.

### 6.3. Запуск Hub Server

- Hub Server работает как самостоятельный процесс Linux. Для развёртывания используется **`systemd`**, который может автоматически перезапустить процесс после аварийного завершения.
- При старте сервер создаёт локальный сокет, пустые хранилища значений/подписок и начинает принимать соединения.
- При штатной остановке закрывает соединения и освобождает ресурсы.
- Для разработки допустим ручной запуск исполняемого файла.
- **В V1 не создаём** отдельный менеджер процессов, специальный административный API перезапуска или сервис мониторинга хаба. Возможность добавить их в будущем **не исключаем**, но заранее под них функциональность не разрабатываем.

## 7. Осознанные ограничения и граница технического этапа

### 7.1. Ограничения первой версии

- Нет MQTT-совместимости, удалённых клиентов, сетевых API и плагинов для конкретного оборудования.
- Нет постоянного хранения, истории, отложенной доставки, регистрации метрик, владельцев ID, ролей и прав доступа.
- Нет обязательных подтверждений каждого Publish, доставки «как минимум один раз» или ожидания завершения Get.
- Нет серверных очередей доставки для медленных клиентов; заполненный системный буфер приводит к отключению соответствующего клиента.
- Нет отслеживания `Clear(..., true)` для клиентов, которые уже отключились.
- Значение метрики и подписки — независимые сущности; Clear не запрещает повторную публикацию того же ID.

### 7.2. Детали, оставленные для технического проектирования / Codex

- Конкретный макет бинарного кадра, порядок байтов и размер заголовка; допустимые максимальные размеры кадров и строк.
- Точные числовые коды операций/служебных уведомлений, формат списков ID и обнаружение обрезанных кадров.
- Организация потоков **Client Library**, реализация callback и решение о необходимости ограниченной входящей очереди.
- Реализация потокобезопасного публичного API, сборка и тесты.

Эти детали **не дают права добавлять новые функции хаба**, менять декадное кодирование ID или разворачивать сервер за пределами одной Linux-машины без нового согласования.

### 7.3. Текущий этап

Этап **II «Архитектура Universal Hub» завершён**. Этап **III «Техническое проектирование» согласован**: C++20, CMake, отдельный репозиторий, Client Library, тестирование и критерии готовности закреплены в документе «Технический план Universal Hub — V1». Разработка исходного кода выполняется отдельно в Codex. Документы диспетчеризации V1 не изменяются.
