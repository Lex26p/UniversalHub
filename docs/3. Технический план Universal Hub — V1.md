# Universal Hub + C++ Client Library — технический план V1

**Статус:** согласовано, 17 октября 2026 года.  
**Назначение:** собрать выбранные технологии, требования к проекту, испытаниям и готовому результату для реализации в Codex.  
**Обязательные документы:** «Концепция Universal Hub — V1» и «Архитектура Universal Hub — V1». При расхождении технических деталей разработчик сверяется с ними; принципиальные изменения согласуются отдельно.

> Universal Hub V1 — **первая версия самостоятельного хаба**, а не диспетчеризация V1. Первая версия диспетчеризации завершается на MQTT; новый хаб будет интегрироваться позже, с допустимой переработкой приложения. Хаб не проектируется специально для диспетчеризации.

## 1. Технологии и среда разработки

| Область | Принятое решение |
|---|---|
| Язык | **C++20** |
| Платформа исполнения | **Linux**, локальные процессы одной машины |
| Разработка и тестирование V1 | **Windows + WSL2, Linux x86-64** |
| Сборка | **CMake**, один корневой проект |
| Зависимости | По возможности **стандартная библиотека C++ и системные API Linux**, без сторонних библиотек |
| Транспорт | **Unix Domain Sockets, SOCK_SEQPACKET**, двунаправленное соединение |
| Мультиплексирование в сервере | **epoll**, неблокирующий ввод-вывод, один событийный поток |
| Протокол | Собственный компактный **бинарный**, без совместимости с MQTT |
| Управление процессом в установке | **systemd**, при разработке возможен ручной запуск |
| ARM / Wiren Board | **Не входит в обязательную проверку первой версии хаба** |

Используем относительно современные стабильные инструменты. Конкретную версию компилятора выбирает Codex, обеспечив полноценную поддержку используемого C++20. Не добавляем внешние зависимости ради гипотетического удобства. Если существенная библиотека всё же потребуется, причину необходимо обосновать до изменения согласованного стека.

## 2. Организация проекта и повторное использование

- Universal Hub размещается **в отдельном репозитории** как самостоятельный продукт, независимый от исходников диспетчеризации.
- Репозиторий включает **Hub Server**, **C++ Client Library**, **общий код протокола** и **тесты/нагрузочные средства**.
- Hub Server собирается в **исполняемый файл**; Client Library — в **статическую библиотеку**.
- Исходники Client Library можно включить в другой **CMake-проект** и собрать вместе с ним без копирования кода сервера.
- Публичный интерфейс библиотеки небольшой и отделён от внутренней реализации сокетов и протокола.
- Обе части используют **одну версию протокола** и обновляются согласованно; поддержку нескольких старых версий пока не разрабатываем.
- Никаких обязательных скачиваний зависимостей во время сборки. Исходники проекта и необходимый общий код находятся в репозитории.

Возможная **логическая** организация (не обязательное точное дерево файлов):

```text
universal-hub/
├── server/        # исполняемый сервис
├── client/        # C++ Client Library
├── protocol/      # общие определения и кодирование сообщений
├── tests/         # автоматические и интеграционные проверки
└── CMakeLists.txt
```

Конкретные классы, исходные файлы, внутренние интерфейсы и порядок разработки определяет Codex.

## 3. Согласованный функциональный состав V1

### 3.1. Идентификаторы и данные

- **ID:** `uint32_t`. Последняя **десятичная** цифра: `0` — передача без хранения; `1` — передача и хранение последнего значения. Остальные окончания пока зарезервированы.
- Предпоследняя **десятичная** цифра: `0` — `int64_t`, `1` — `double`, `2` — UTF-8 строка; прочие коды пока зарезервированы.
- Дополнительное поле типа или режима в каждой публикации **не требуется**; клиентская библиотека предоставляет строго типизированные операции и проверяет динамические ID, где компилятор не может сделать это заранее.
- Приём/сохранение значения — только по числовому ID, без строковых топиков, регистрации метрик или привязки к конкретному оборудованию.

### 3.2. Основные операции

| Операция | Согласованное поведение |
|---|---|
| `Publish(ID, value)` | Доставить публикацию подписчикам и, при режиме `1`, заменить последнее хранимое значение |
| `Subscribe([IDs])` | Подписаться на числовые ID, получить доступные последние сохранённые значения и далее новые публикации |
| `Unsubscribe([IDs])` | Снять собственные подписки |
| `Get([IDs])` | Послать имеющиеся последние значения **только вызывающему клиенту** обычными входящими сообщениями; без ожидания завершения и без сообщений об отсутствующих значениях |
| `Clear([IDs], false)` | Удалить последние значения, оставить подписки без изменений, не уведомлять подписчиков |
| `Clear([IDs], true)` | Удалить значения, отменить текущие подписки на ID и передать затронутым клиентам служебное уведомление об отмене |

При `Clear(..., true)` Client Library удаляет затронутые ID из списка автоподписок и вызывает обработчик уровня приложения вроде **`onIdRemoved(id)`**. Удаление не запрещает новые публикации/подписки; событие для клиента, уже отключённого в момент Clear, не запоминается.

### 3.3. Доставка и хранение

- Для публикаций, начальных значений после подписки и результатов `Get` используется **один формат входящего Value и один callback** клиента.
- Повторяющиеся публикации не сравниваются на стороне хаба; фильтрация — ответственность отправителя.
- Для подписок используем индексы **ID → подписчики** и **клиент → ID** без двойных доставок при повторном Subscribe.
- Последние значения находятся **только в RAM** (`std::unordered_map<uint32_t, Value>`, где Value представлен `std::variant<int64_t, double, std::string>`), а не на диске.
- Несохраняемые ID никогда не создают записей в Values; при перезапуске хранилище пустое. Значения удаляются через Clear либо заменяются новой публикацией.
- Нет истории значений, гарантированной доставки, отложенных публикаций или постоянных клиентских сессий.

### 3.4. Поведение соединений

- **Один Hub Server-процесс** и **одно UDS-соединение на экземпляр Client Library**; публичные операции библиотеки потокобезопасны.
- Hub Server обслуживает соединения через **один событийный поток** и `epoll`; медленное соединение не блокирует остальные.
- В Hub Server **не создаются отдельные прикладные очереди доставки**. При невозможности немедленной отправки из-за заполненного системного буфера проблемный клиент отключается.
- Client Library автоматически обнаруживает разрыв, уведомляет приложение, переподключается и восстанавливает **актуальные подписки**.
- Операции, которые не удалось отправить при недоступном хабе, **не накапливаются** для выполнения после восстановления связи.
- Client Library не дублирует последние значения в своём кеше. **Небольшая ограниченная очередь приёма** в Client Library допустима, но не обязательна; детали определяет Codex в соответствии с условиями памяти и обработки callback.

## 4. Тестирование — обязательное для Codex

### 4.1. Автоматические тесты

Codex реализует и запускает повторяемые проверки основных операций (`Publish`, `Subscribe`, `Unsubscribe`, `Get`, оба варианта `Clear`), трёх типов данных, двух режимов хранения, нескольких клиентов, переподключения, отмены подписок и `onIdRemoved`.

### 4.2. Практический запуск

**Одних автоматических тестов недостаточно:** Codex должен **самостоятельно собрать, запустить Hub Server и тестовые клиентские приложения в WSL2**, проверить фактический обмен значениями, состояния соединений и результаты операций. Детализацию проверок и исправление ошибок выполняет агент.

### 4.3. Нагрузочное тестирование

В состав проекта входит небольшая утилита для измерения:

- числа публикаций и доставленных сообщений за секунду;
- задержки от публикации до получения подписчиком;
- потребления CPU и оперативной памяти;
- зависимости показателей от числа подписчиков и метрик.

**Произвольных нормативов не назначаем.** Результаты должны быть измерены и зафиксированы. Очевидные проблемы производительности, выявленные испытаниями, Codex анализирует и исправляет в разумных пределах без микрооптимизаций ради отдельных наносекунд.

### 4.4. Длительные испытания

Codex самостоятельно проводит длительный запуск с обменом сообщениями, оценивает стабильность, необъяснимый рост памяти, зависания и деградацию производительности. Конкретную продолжительность и сценарии выбирает агент, результаты фиксирует.

**Среда обязательной проверки:** **WSL2, Linux x86-64**. Отдельные испытания на ARM и Wiren Board в первую версию Universal Hub не включаются.

## 5. Критерии приёмки Universal Hub V1

Первая версия **готова**, когда выполнены все следующие условия:

1. **Сборка:** Hub Server и Client Library собираются через CMake в WSL2/Linux x86-64, причём Client Library собирается и используется отдельно от кода Hub Server.
2. **Повторное использование:** независимое C++20 тестовое приложение может подключить статическую Client Library и обмениваться данными с работающим Hub Server.
3. **Базовые операции:** проверены `Publish`, `Subscribe`, `Unsubscribe`, `Get`, `Clear(false)` и `Clear(true)` для одного и нескольких ID.
4. **Типы и режимы:** проверены `int64_t`, `double`, UTF-8 string и оба режима ID (Stored/Transient), без дополнительной регистрации метрик.
5. **Многоклиентская работа:** несколько приложений одновременно публикуют и получают значения по выбранным подпискам; `Get` отправляет значения только запрашивающему.
6. **Жизненный цикл:** проверены разрывы соединения, переподключение, восстановление подписок, принудительная отмена с `onIdRemoved` и отсутствие накопления отложенных действий.
7. **Автоматические и практические проверки:** Codex выполнил тесты и непосредственный запуск приложения, получил ожидаемые результаты и исправил обнаруженные ошибки.
8. **Производительность и стабильность:** проведены нагрузочные и длительные испытания, результаты документированы, существенные проблемы проанализированы.
9. **Минимальная документация:** есть инструкции по сборке/запуску, подключению Client Library, её публичному API и результатам испытаний.

## 6. Что должно быть передано по завершении реализации

- Исходники самостоятельного проекта Universal Hub с CMake и Client Library.
- Исполняемый Hub Server, собираемая статическая библиотека и тестовые/нагрузочные инструменты.
- Краткая инструкция сборки, запуска и подключения библиотеки в сторонний CMake-проект; несколько примеров публичных операций.
- Результаты автоматических, интеграционных, нагрузочных и длительных проверок — с указанием условий и фактически полученных результатов (не выдуманные показатели).

Никакие объёмные UML-пакеты, отдельные руководства для каждого класса и новая инфраструктура не требуются.

## 7. Что оставляем Codex

Codex самостоятельно проектирует классы, конкретный макет бинарного кадра, порядок байтов, точные коды операций, предельный размер пакета, раскладку файлов, детали callback/очередей, внутренние тестовые сценарии и разбиение работы на задачи.

При этом Codex **не должен самостоятельно расширять продукт**: сохраняются десятичное кодирование типа/режима в ID, асинхронный `Get`, отсутствие отдельного Request/Reply, один локальный транспорт, единый механизм поступления значений, отсутствие клиентских очередей отложенных публикаций и согласованное поведение `Clear`.

**Не реализуем в V1:** MQTT и TCP-доступ, регистрационные каталоги метрик, хранение истории и значений на диск, гарантированную доставку, систему пользователей, кластеризацию, специальные административные API или функциональность конкретных промышленных устройств.

**Рабочее правило:** в этом чате согласовывается продукт; реализацию и самостоятельную проверку кода выполняет Codex. При выявлении принципиальной архитектурной проблемы она согласуется отдельно; обычные инженерные решения агент принимает самостоятельно.
